# M6: userspace drivers and the initramfs

Date: 2026-11-02. Driver: Claude (Fable 5.1). Navigator: Andre.

## What exists now

- **Device discovery** (`devices.rs`): walks the device tree at any depth
  (QEMU keeps its transports under `/soc`) for nodes compatible with
  `virtio,mmio`, probes each slot's magic and device id, and registers the
  ones that have a device behind them. Each becomes a `Device` object
  (`obj/device.rs`): a register window, an interrupt line, and a virtio
  device id, logged as a `device` event at boot.
- **Interrupt policy for user drivers.** When a device's line fires, the
  kernel masks the source at the PLIC, counts the interrupt and wakes the
  driver. `device_irq_wait` returns the count; `device_irq_ack` unmasks.
  A level-triggered line therefore cannot storm while a driver is slow.
- **Three device syscalls**: `device_map` (the register window, read-write),
  `device_irq_wait` (with timeout), `device_irq_ack`. Twenty-four syscalls
  in all.
- **DMA capability**: `vmo_create` takes a `CONTIGUOUS` flag, and
  `vmo_physical` returns a byte's physical address for such a VMO. The
  `map` right gates it; give it to drivers only.
- **Initramfs**: `cargo xtask build` packs the user programs into a `newc`
  cpio archive, which the kernel embeds in place of individual ELFs. The
  kernel pulls `init` out of it (`sprout-abi::cpio`, shared with
  userspace) and hands `init` the whole archive as a VMO, followed by a
  handle per discovered device.
- **`fsd`**: receives the archive over its channel, maps it, and answers
  `open <name>` with a fresh VMO holding the file. `init` spawns `fsd`
  from the archive directly and every other program through `fsd`.
- **`sprout-virtio`** (`lib/sprout-virtio`): the modern virtio-mmio
  transport (version 2, `VERSION_1` negotiated), one split virtqueue over
  caller memory, and the virtio-blk one-sector request. No allocation, no
  syscalls; the driver supplies mapped memory and physical addresses.
- **`blkd`**: a virtio-blk driver as an ordinary process. It maps the
  device, brings it up, reads sector 0 (checking the disk image's magic),
  writes sector 1 and reads it back, each request completed by the
  device's interrupt through `device_irq_wait`.
- **xtask**: creates `target/disk.img` (1 MiB, magic at sector 0) and
  boots QEMU with `virtio-mmio.force-legacy=false` and a `virtio-blk-device`.

## Decisions made along the way

- **One `Device` object instead of separate `Interrupt` and MMIO objects.**
  PLAN.md 2.1 lists an `Interrupt` object; a device is the unit a driver is
  handed, and the register window and the line always go together.
- **Mask on interrupt, unmask on ack.** The alternative, letting the
  driver clear the device's own interrupt status before the kernel
  completes the claim, needs the driver to run inside the interrupt, which
  a userspace driver cannot.
- **Modern virtio-mmio only.** QEMU defaults its virtio-mmio transports to
  the legacy (version 1) register layout; `force-legacy=false` selects
  version 2, which has 64-bit queue addresses and a cleaner feature
  handshake. Real hardware is modern too.
- **Device discovery walks every depth.** The first version looked only at
  the root's children and found nothing because QEMU nests devices under
  `/soc`. The device-discovery test would have caught a regression; it
  caught the original.
- **No virtio-console driver.** The SBI console already carries the log
  and the UART receive path carries input; a second console would add two
  queues of code for no new capability. Dropped from M6 on purpose.
- **`init` gets every device.** Capability-wise this is the root of the
  tree: `init` decides which driver gets which device, and gives `blkd` a
  duplicate rather than its own handle.

## Known limitations

- One request in flight per device; the virtqueue hands out descriptors in
  order and is drained after each request.
- `blkd` proves the driver model and exits; it does not yet stay resident
  and serve block requests to other processes over a channel.
- `fsd` copies each file into a new VMO per `open`; fine for a dozen files.
- A driver is trusted with DMA: `vmo_physical` gives it addresses the
  device can write anywhere in RAM through. An IOMMU is far off; keep
  the `map` right away from everything that is not a driver.
- The initramfs is still embedded in the kernel; loading it from the disk
  needs a filesystem on the disk first.
