# M8: second architecture, x86_64

Date: 2026-11-02. Driver: Claude (Fable 5.1). Navigator: Andre.

ADR-0002 bet that keeping architecture-specific code behind a small surface
would make the second port additive. This milestone cashes that bet: the
same kernel, user programs and test suite now run on x86_64, booted by a
Multiboot loader, with every kernel test passing on both machines.

## What exists now

- **A portable hand-off** (`kernel/src/handoff.rs`). Each architecture
  turns whatever its loader gave it into one `Handoff`: RAM regions,
  reserved regions, the clock rate and, where there is one, a device tree.
  `kmain` takes no arguments; it calls `arch::handoff()` after the console
  is up. On riscv64 that parses the FDT from OpenSBI; on x86_64 it reads
  the Multiboot memory map and measures the TSC against the PIT.
- **`kernel/src/arch/x86_64/`**, 1,519 lines against riscv64's 1,508:
  - `boot.rs`: Multiboot 1 header with the a.out kludge (QEMU and GRUB load
    the file flat at 1 MiB and clear `.bss`), 32-bit entry, boot page
    tables in assembly, long mode, jump to the high half.
  - `gdt.rs`, `idt.rs`: flat segments for ring 0 and 3, a TSS whose `rsp0`
    the scheduler keeps current, 256 interrupt stubs feeding one
    `TrapFrame`. Exceptions, legacy IRQs on vectors 32 to 47, syscalls on
    `int 0x80` (rax number; rdi, rsi, rdx, r10, r8, r9 arguments).
  - `pic.rs`, `pit.rs`, `serial.rs`, `ports.rs`: the 8259 pair remapped,
    the 8254 at 100 Hz on IRQ 0, COM1 as console with its receive
    interrupt, and the three port-I/O instructions behind them.
  - `paging.rs`: four-level tables, 4 KiB and 2 MiB pages, NX. The image
    sits in the top 2 GiB (`IMAGE_OFFSET`, the `kernel` code model) and
    the direct map at the same `PHYS_MAP_BASE` as riscv64, so
    `virt_to_phys` branches on the range. User tables copy the upper half
    of the PML4.
  - `context.rs`, `user.rs`, `backtrace.rs`, `exit.rs`, `handoff.rs`:
    callee-saved switch, `iretq` into ring 3, frame-pointer walking,
    `isa-debug-exit`, and the Multiboot reader.
- **Portable code that learned the difference.** `mm::build_kernel_table`
  asks `arch::supports_page_size` (no 1 GiB pages on x86) and
  `arch::map_platform` (riscv64 maps the device GiB; x86_64 adds the image
  to the direct map). The ELF loader checks `e_machine` for the running
  architecture. Device discovery runs only with a device tree; `init`
  reports block and network checks as skipped when the device is absent.
  `arch::EXIT_CODE_INSTRUCTION_FAULT` names the code a process gets for
  jumping to an unmapped address (128 + 12 on riscv64, 128 + 14 on x86).
- **`sprout-rt`** has an x86_64 `_start` and `int 0x80` stub; user
  programs are otherwise unchanged. The user linker script dropped its
  `OUTPUT_ARCH` and folds `.got` into `.rodata`.
- **Build and tooling.** `kernel/linker-riscv64.ld` and
  `kernel/linker-x86_64.ld`, chosen by `build.rs` from the target.
  `.cargo/config.toml` gives x86_64 frame pointers, a static relocation
  model and the `kernel` code model. Every `cargo xtask` command takes
  `--arch riscv64|x86_64` (or `SPROUT_ARCH`); the x86 QEMU line is the
  default `pc` machine with `-kernel` and `isa-debug-exit`, no virtio.
  The dev MCP server's `build`, `boot`, `test`, `symbolize` and `lint`
  take an `arch`. CI is a two-architecture matrix; `mcp-check` runs on
  riscv64 only. `loc` reports each architecture against its own target.

## Verified

| Check | riscv64 | x86_64 |
|---|---|---|
| `cargo xtask test` | 57 passed, 0 failed | 48 passed, 0 failed |
| `cargo xtask run`: `init` runs every check (block and network skipped on x86) | ok | ok |
| `cargo xtask mcp-check` | ok | not applicable (no NIC) |
| `cargo xtask lint` | ok | ok |
| Backtraces symbolize (`xtask symbolize`) | ok | ok |
| Faulting process gets the right exit code | 140 | 142 |

The x86 test count is lower because the FDT, PLIC, SBI and device tests
are riscv64-only, and the x86 port has no equivalent of the device tests
yet.

## Bringing it up

Five bugs between the first link and a green gate, each found by the
existing log and backtrace machinery within one boot:

1. `push offset sym` in 32-bit code assembled to a 16-bit immediate; load
   through a register first.
2. The direct map's PML4 slot: `0xffffffc000000000` lives in PML4[511],
   PDPT[256], not in its own PML4 entry as the riscv Sv39 numbers suggest.
3. An orphan `.got` section landed between `.rodata` and `.data`, so
   `.data` was not page-aligned and the kernel table build failed with
   `Misaligned`.
4. `pic::init` masked every line after `time::init` had unmasked the timer,
   so the first test that slept hung. The PICs now come up in `init_early`.
5. The backtrace walker's bounds check overflowed on a deliberately bad
   frame pointer; it now uses `checked_add`.

## Decisions made along the way

- **Multiboot 1, not Limine or UEFI** (ADR-0007). QEMU's `-kernel` loads a
  Multiboot ELF directly, which keeps the x86 loop as short as the riscv
  one and needs no image building on Windows. GRUB speaks it too.
- **Legacy devices first.** 8259, 8254, COM1 and `int 0x80` are a few
  dozen lines each and work on every x86 machine and hypervisor. The local
  APIC, HPET, `syscall`/`sysret` and virtio-pci are each a separate step.
- **One `PHYS_MAP_BASE` for both architectures.** The direct map address
  is shared; only the image's own address differs. Portable code never
  cares which.
- **Shared boot page directory.** The first GiB is mapped three times by
  the boot tables (identity, direct map, image alias) with one page
  directory of 2 MiB entries. `mm::init` replaces it within the first
  few milliseconds.

## Known limitations

- No devices on x86_64: virtio-pci needs PCI enumeration and a transport
  in `sprout-virtio`, so `blkd` and `mcpd` do not run there yet.
- No SMP on either architecture (PLAN.md's M8 row asked for it; moved to
  M9+).
- Legacy PIC and PIT only; no APIC, so no IRQs above 15 and a 100 Hz tick
  that cannot be programmed per deadline (`set_timer` is a no-op).
- Multiboot 1 limits the kernel to below 4 GiB physical and to BIOS boot.
  A laptop with UEFI-only firmware needs a Multiboot 2 or Limine path.
- Direct map covers physical addresses up to the image alias (254 GiB), and
  only the first GiB before `mm::init`.
