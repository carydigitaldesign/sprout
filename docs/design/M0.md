# M0: toolchain and MCP dev loop

Date: 2026-11-02. Driver: Claude (Fable 5.1). Navigator: Andre.

## What exists now

- A riscv64 kernel that OpenSBI loads at `0x80200000`, which sets up a stack,
  clears `.bss`, probes the SBI, prints a JSON boot line, and stops QEMU with
  a status code through the SiFive test finisher.
- Structured logging (`kernel/src/log.rs`): every console line is one JSON
  object, with values escaped so the output always parses.
- A test harness on stable Rust (`kernel/src/testing.rs`): `ktest!` places a
  `TestCase` in a linker section, the test kernel walks that table, prints one
  JSON line per test and exits 0 or 1. A panic inside a test reports the test
  name, message, file and line.
- `cargo xtask` with `build`, `run`, `test`, `qemu-args`, `loc` and `lint`.
  Build logic lives nowhere else.
- `tools/mcp-dev/server.py`, registered in `.mcp.json`: `build`, `boot`,
  `serial_read`, `serial_write`, `stop`, `sessions`, `test`, `gdb_inspect`,
  `loc`, `lint`.
- A GitHub Actions workflow that runs lint, the QEMU test gate and loc on
  Ubuntu. Not yet exercised: the repo has no remote.

## Verified

| Check | Result |
|---|---|
| `cargo xtask run` | Boot line `{"event":"boot","kernel":"0.1.0","arch":"riscv64","hart":0,"dtb":"0x87e00000","console":"sbi-dbcn"}`, then a clean exit with code 0. |
| `cargo xtask test` | 4 tests pass; summary line reports `ok: true`; process exit 0. |
| Failure path | A deliberately failing test produced `{"test":...,"ok":false,"panic":"assertion ... failed ...","file":...,"line":...}`, exit event 1, QEMU exit 1, xtask exit 1. Removed afterwards. |
| `cargo xtask lint` | Every `unsafe` block carries a `// SAFETY:` comment. |
| MCP server | A Python stdio client listed all ten tools, ran `lint` and `test` (both ok), booted a session, read its console and stopped it. |

The `until` argument of `serial_read` was not exercised in anger, because the
M0 kernel exits within the boot call's settle window. It gets real use at M1
when the kernel idles.

## Decisions made along the way

- **Boot stack is 64 KiB** reserved in the linker script after `.bss`.
- **SBI debug console (DBCN) with legacy putchar fallback**, probed once at
  boot. QEMU 11's OpenSBI has DBCN.
- **Exit through the SiFive test finisher first, SBI shutdown second.** The
  finisher is reachable from S-mode under OpenSBI, so QEMU's exit status
  carries the kernel's code. `xtask test` still judges by the JSON `exit`
  event, not the process status, so a firmware that blocks the finisher only
  loses the convenience.
- **Test kernel builds into `target/ktest`**, so switching between the normal
  and test kernels does not rebuild the world.
- **Host toolchain is windows-gnu** on the navigator's machine (ADR-0005).
- **Toolchain pinned at 1.99.1.**

## Known limitations

- A failing test ends the run; tests after it do not execute. Isolating tests
  needs trap handling, which arrives at M3.
- No GDB client is installed yet, so `gdb_inspect` returns install
  instructions rather than registers.
- The old OneDrive folder is empty but still held open by a process and could
  not be deleted; it can go whenever that handle is released.
