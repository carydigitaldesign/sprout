# M2: memory

Date: 2026-11-02. Driver: Claude (Fable 5.1). Navigator: Andre.

## What exists now

- **Higher-half kernel.** The image is linked at `0xffffffc080200000`
  (physical `0x80200000` plus the direct-map base) with physical load
  addresses, so QEMU still places it at `0x80200000` and jumps to the lowest
  load address. The first instructions in `boot.rs` turn on Sv39 with a
  compile-time page table of 1 GiB entries (identity and direct map of the
  first 4 GiB) and jump to the high alias of the next instruction. Every
  address from then on is the linked one.
- **Direct map.** Physical address `p` is reachable at
  `PHYS_MAP_BASE + p` (`arch::phys_to_virt`). All RAM and the first GiB of
  device space are mapped there read-write. The kernel image's virtual
  addresses coincide with their direct-map addresses, which keeps
  `virt_to_phys` a subtraction.
- **Device tree reader** (`fdt.rs`): a token walker over the blob in place
  and a `memory_regions` helper. RAM base and size come from the firmware,
  not from a constant. Tested against a hand-built blob and the real one.
- **Frame allocator** (`mm/frame.rs`): one bit per 4 KiB frame over the RAM
  after the kernel image, bitmap stored in its own first frames, device tree
  blob reserved. `alloc`, `alloc_zeroed`, `alloc_contiguous`, `free`,
  `stats`. Double frees panic.
- **Sv39 page tables** (`arch/riscv64/paging.rs`): `PageTable` with `map`
  (4 KiB, 2 MiB, 1 GiB), `unmap`, `translate`, `activate`; intermediate
  tables are allocated on demand and freed on drop. Leaf entries carry A and
  D up front so a core without hardware A/D updates never faults on them.
- **Kernel page table** (`mm/mod.rs`): text read+execute, rodata read-only,
  data/bss/stack read-write, 4 KiB granularity; the rest of RAM and the
  device GiB in the direct map with large pages where alignment allows. It
  replaces the boot table before anything else runs, and the identity
  mapping goes with it: address 0 and the physical kernel address are
  unmapped.
- **Kernel heap** (`mm/heap.rs`): 1 MiB from the frame allocator behind
  `linked_list_allocator` and the kernel's own `SpinLock` (ADR-0006).
  `alloc::{Box, Vec, String}` work.
- **`Vmo`** (`mm/vmo.rs`): a vector of zeroed frames with `read`, `write`,
  `resize`, `frame`; frees its frames on drop.
- **`SpinLock`** (`sync.rs`): a spinlock with a stuck-lock panic. Not yet
  interrupt-safe; M3 adds that when it enables interrupts.

## Decisions made along the way

- **Direct-map base `0xffffffc000000000`** (the bottom of Sv39's upper
  half), covering up to 256 GiB of physical space.
- **Boot table maps 4 GiB with 1 GiB pages, both identity and direct.** More
  than QEMU has; the kernel table built from the device tree is what
  matters after boot.
- **Kernel image mapped with 4 KiB pages** so each section gets its own
  permissions; everything else uses 2 MiB and 1 GiB pages.
- **`Frame` is `Copy` and not `Drop`.** Ownership is by convention
  (whoever allocated frees), which keeps page-table code simple. `Vmo` is the
  owning wrapper.
- **One kernel dependency**, `linked_list_allocator`, written up in
  ADR-0006.

## Known limitations

- Only the first `memory` region of the device tree is managed.
- `unmap` keeps empty intermediate tables; they are freed with the table.
- The heap is a fixed 1 MiB; no growth yet.
- The frame allocator is a bitmap; `alloc_contiguous` is a linear scan.
  Buddy allocation waits for a real need.
- `SpinLock` does not mask interrupts (none are enabled yet).
