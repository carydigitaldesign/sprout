# M7: network and the in-OS MCP server

Date: 2026-11-02. Driver: Claude (Fable 5.1). Navigator: Andre.

This is the milestone PLAN.md was aimed at: an agent on the host speaks
the Model Context Protocol to a server running inside Sprout, and that
server's tools reach the kernel and a shell.

## What exists now

- **virtio-net in `sprout-virtio`**: the virtqueue gained a descriptor
  free list so several chains can be in flight; `NetDevice` runs a receive
  queue with four posted buffers and a transmit queue with one, negotiates
  `VERSION_1` and `MAC`, and reads the MAC from config space.
- **`mcpd`** (`user/mcpd`): owns the network device, runs `smoltcp` on it
  (fixed buffers, no heap: Ethernet, IPv4, TCP, static address 10.0.2.15
  with 10.0.2.2 as gateway, which is QEMU user networking), listens on port
  80 with a pool of three sockets, parses one HTTP POST per connection and
  answers JSON-RPC per MCP's streamable HTTP transport: `initialize`
  (echoing the client's protocol version), `ping`, `tools/list`,
  `tools/call`; notifications get `202 Accepted`. Tools: `kernel` (the
  kernel's description), `handles` (what mcpd holds), `shell` (a command to
  a shell over a channel), `log` (a line on the kernel log). JSON is
  scanned and written without allocation (`json.rs`).
- **`init`** finds the network device, spawns a second `shell` and `mcpd`,
  hands `mcpd` the device and the shell's channel, and waits for `ready`.
  In the test kernel it then tells `mcpd` to exit; in a normal boot it
  stays up as `mcpd`'s parent while `mcpd` serves.
- **Kernel**: `clock_ns` (syscall 24) for protocol timers, and a `mode`
  field in the kernel's description (`test` or `run`) so `init` can tell
  the two apart. In run mode `kmain` no longer waits for `init`.
- **xtask**: QEMU gets a `virtio-net-device` on user networking with host
  port 8080 forwarded to guest port 80, and a new `mcp-check` command boots
  the kernel, waits for `mcpd: listening`, and speaks MCP from the host.
  CI runs it. The dev MCP server has an `mcp_check` tool.

## Verified

| Check | Result |
|---|---|
| `cargo xtask test` | 56 tests pass; `init` brings `mcpd` up (`virtio-net up, mac 52:54:00:12:34:56`, `listening on 10.0.2.15:80`), gets `ready`, tells it to exit, and both it and its shell exit 0. Frames and threads balance afterwards. |
| `cargo xtask mcp-check` | From the host over TCP: `initialize` answers with `serverInfo.name = "sprout"`; `tools/list` returns the four tools; `tools/call shell {"command":"ping"}` returns `pong` (host to `mcpd` to shell and back); `tools/call kernel` returns the 7.6 KB kernel description containing `clock_ns`. |
| Back-to-back connections | With one socket every other request failed: a new SYN arrived while the previous connection was still closing. Three sockets, each re-listening when closed, fixed it. |
| Double handling | Each request was processed twice because a half-closed socket still reports it may receive and the buffer still held the request. Clearing the request buffer once a response is built fixed it. |

## Using it

With a kernel running (`cargo xtask run`, or the dev server's `boot`):

```
claude mcp add --transport http sprout-os http://127.0.0.1:8080/mcp
```

Then Claude Code lists `kernel`, `handles`, `shell` and `log` as tools of a
server that lives inside the OS it helped build.

## Decisions made along the way

- **`mcpd` owns the NIC and the stack.** PLAN.md M7 named a separate
  `netd` with `mcpd` as its client; that needs a socket API over channels,
  which is a milestone of its own. One process that is both is the
  smallest thing that proves the point. Splitting it is the natural next
  step once a second network client exists.
- **No heap in userspace, still.** `smoltcp` runs on fixed buffers, HTTP
  and JSON-RPC use fixed buffers, and the JSON scanner finds the first
  occurrence of a key, which is right for every message MCP sends here.
- **One request per connection, `Connection: close`.** MCP clients open a
  connection per POST anyway; keep-alive and SSE streams can come later.
- **Static IP.** QEMU user networking always gives 10.0.2.15; DHCP would be
  another protocol for no gain until real networks.
- **The kernel tells `init` which build it is.** The alternative, a build
  flag threaded into `init`, would mean two `init` binaries.

## Known limitations

- One network client in the system: nothing else can open a socket.
- One request per connection; no SSE stream, so no server-initiated
  notifications; no `MCP-Session-Id`.
- The JSON scanner is first-match: a tool argument literally named `id`
  or `method` would confuse it.
- Responses are capped at 12 KiB, so a future tool returning more must
  page.
- `mcpd` polls the NIC every 10 ms on top of interrupts; fine for a
  demo, wasteful for a battery.
- User networking is NAT: the host reaches the guest only through the
  forwarded port.
